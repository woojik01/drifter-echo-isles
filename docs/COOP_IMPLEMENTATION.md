# Drifter 1.2.0 co-op 구현 안내

## 구성

- 브라우저 클라이언트: CrazyGames HTML5 + 로컬로 번들된 Colyseus JavaScript SDK
- 실시간 서버: Node.js/TypeScript, Colyseus 0.18, Schema 5, WebSocket 전송
- 호스팅 청사진: `render.yaml`의 Render 무료 Web Service
- Sites 배포 설정: `/api/coop-config`가 `DRIFTER_COOP_SERVER_URL`을 읽음
- 이전 Supabase SQL 마이그레이션은 v1.1.x 이력 보존용이며 v1.2.0에서 실행하지 않음

## 방과 동기화

방 코드는 8자리이고 기본 정원은 4명입니다. 방 생성 요청은 재시도해도 중복 방을 만들지 않도록 짧은 idempotency 키를 사용합니다. 방장은 새 방을 시작하거나 방을 닫고, 클라이언트는 방장 위치와 월드 시드를 방 옵션으로 전달합니다. 연결 재개 토큰은 브라우저에 보관하고, 서버가 살아 있는 동안 Colyseus 재접속에 사용합니다.

플레이 중 이동 전송은 프레임 루프와 분리된 제한 주기로 변경된 상태만 보내며, 원격 플레이어 위치는 보간합니다. 같은 방의 참가자만 Colyseus 상태를 받습니다. 월드 자원 타격은 서버가 타깃 종류와 피해량을 확인하고 노드 상태를 반영합니다. 적은 현재 시뮬레이션 담당 클라이언트가 제한된 수의 상태 스냅샷을 보냅니다. 바닥 아이템은 서버에 등록하고, 원자적인 방 상태 변경으로 한 명만 획득하도록 조정합니다. 정적 월드 지형 전체는 전송하지 않고 공유 시드에서 생성합니다.

싱글플레이 전투·경험치·보상 루프는 기존 클라이언트 엔진을 유지합니다. 따라서 이 빌드는 서버 검증을 갖춘 초대형 협동 미리보기이며, 모든 게임 경제가 서버 권한으로 이전된 경쟁용 서버는 아닙니다. 공개 랭킹/PvP/거래에는 사용하면 안 됩니다.

## 서버 배포와 클라이언트 연결

1. `render.yaml`의 Blueprint가 비공개 GitHub 저장소에 연결되어 Render 무료 Web Service를 배포합니다.
2. 배포 주소 `https://drifter-colyseus.onrender.com`의 `/health`에서 `{ "ok": true, "service": "drifter-colyseus" }` 응답을 확인했습니다.
3. CrazyGames 빌드의 `game-assets/coop-config.js`에는 이 주소가 설정되어 있습니다.
4. Sites Worker에서는 런타임 환경 설정 `DRIFTER_COOP_SERVER_URL`을 추가하고 Worker를 다시 배포합니다. 주소는 공개값이며, 서버용 관리자 비밀은 브라우저에 전달하지 않습니다.

클라이언트는 사용자가 방을 만들거나 참가할 때만 서버를 깨우기 위해 `/health`를 요청합니다. 최대 대기 시간은 120초, 재시도 간격은 상한이 있는 지수 백오프이며 사용자는 취소할 수 있습니다. 유휴 중에는 주기 요청이 없습니다. Render의 무료 인스턴스가 절전 또는 재시작되면 메모리에 있던 방은 복원할 수 없습니다.

## 테스트 기록

`server/test/integration.test.mjs`는 로컬 실제 서버와 Colyseus SDK 클라이언트 4개를 연결해 다음을 검증합니다.

- 8자리 코드로 방 생성과 추가 참가, 공통 시드, 참가자 정원 제한
- 공유 자원 노드 피해, 적 스냅샷/피해 전파
- 바닥 아이템 전달과 중복 획득 차단

로컬 게임 빌드의 별도 브라우저 두 세션으로 실제 Render 서버에 연결해 방 생성·참가·이탈을 확인했습니다. CrazyGames 도메인 Preview에서의 추가 연결 확인, Render 절전 후 복구, 모바일 기기, 장시간 프레임 안정성은 아직 측정하지 않았습니다.

## 운영 한계

Render 무료 서비스는 유휴 시 잠들 수 있고 방 데이터는 메모리에 있습니다. 단일 인스턴스로 배포해야 하며 여러 인스턴스에서 공유할 영속 매치메이커/저장소는 구성하지 않았습니다. 서버 재기동 후 기존 방 코드로 복귀할 수 없고, 클라이언트는 이 경우 솔로 진행으로 돌아갑니다. 실제 공개 운영 전에는 서비스 가용성, 서버 권한형 보상, 인증·남용 방지, 로그/부하 정책을 추가로 설계해야 합니다.
